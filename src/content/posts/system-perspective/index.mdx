Most reviews ask how capable the model is and how to train or prompt it ([Qin et al., 2026](#ref-qin2026)); Li and Yao ([2026](#ref-li2026)) map the agent–environment loop. This post is about the software system around the model. Our test: if swapping the framework while keeping the model changes a property, the property belongs to the system. Whether the VLM recognizes a new cup is about the model; whether a new decision can interrupt a reach under way, or a command that would drive the arm into the table can reach the motors, is about the system.

We name three properties we want from that system, and the two design choices that shape them most.

## A Running Example

The robot is asked to put a cup on a tray, and halfway through the grasp, someone nudges the cup aside.

In a *ReAct-style* system ([Yao et al., 2023](#ref-yao2023)) the model calls one tool at a time, such as `get_position(cup)` and then `grasp(cup)`, and reads each result. In a *code-as-policy* system it writes a short program that calls such tools. A program handles the nudge only if the model anticipated it; a ReAct loop notices only after `grasp` returns. Neither can interrupt an action in progress, and that is a limit of the system, not of the model.

<Figure caption="The running example, from above. Left: a blocking grasp reaches for the old position and closes on nothing before the system looks again. Right: a running grasp task is redirected and follows the cup.">

</Figure>

## Three Properties

### Expressiveness

Can the system express the logic a task needs, and give each decision the information it needs?

**Logic.** Branches, loops, and reuse come free with any programming language. What a plain program lacks is logic that spans physical time: a slip monitor beside a grasp, a handler that fires when the cup moves, an action that continues while the model thinks. That depends on the runtime. The model in Guava ([Liu et al., 2026](#ref-liu2026)), for instance, works through nine fixed tools one call at a time, so a parallel monitor cannot be expressed at all.

<Figure wide caption="Robot tasks need control structures of increasing richness: a single path, branches and loops, and concurrent tasks redirected by events. A system is expressive when the richer ones are as natural to write as the simple one.">
  <Expressiveness />
</Figure>

**Information.** A model knows only what its tools return, and whoever repairs a failed program, a person or a coding agent, needs to know what happened. ASPIRE ([Lu et al., 2026](#ref-lu2026)) records every primitive call with its inputs, outputs, and keyframes; adding this trace alone raises its success on LIBERO-Pro from 14% to 62%.

<Figure wide caption="The same failed run three ways. An error line hides the cause; a full log buries it; a structured trace links the failed action to the decision and the data behind it.">
  <Observability />
</Figure>

### Efficiency

**Utilization**: if every call blocks, the arm waits while the model thinks and the model waits while the arm moves. In Agent as Policy, about 80 seconds of motion overlapped with generation under Codex CLI and none under Claude Code, a difference of harness, not model. **Feedback**: when the cup is nudged, how long does the arm keep reaching for the old position? TypeGo ([G. Chen et al., 2026](#ref-chen2026typego)) runs reflexes at 100 Hz, ReKep ([Huang et al., 2024](#ref-huang2024)) re-solves its constraints at about 10 Hz, and HAMSTER ([Li et al., 2025](#ref-li2025)) plans a path once per episode and cannot adjust it.

### Safety

A failed grasp can be retried; an arm that sweeps the cup through the table, or hits the person who nudged it, cannot be undone. A safe system catches a bad command from any component, which takes three things:

1. **Identification**: recognizing that a command or state is dangerous.
2. **Control authority**: the power to block a command and stop the program that issued it.
3. **Fallback**: a behavior, verified in advance, that brings the robot to a safe state.

Current systems implement pieces inside one component: Code as Policies ([Liang et al., 2023](#ref-liang2023)) rejects `exec` in generated code, ReKep keeps targets in the workspace, and Agent as Policy checks every request against workspace and motion limits. None we surveyed has a safety layer independent of both the model and the generated code.

<Figure caption="A model or program emits a command that would cause irreversible damage. The system identifies it, blocks it and stops the program, and runs a fallback to a safe state.">

## Two Design Choices

### Managing Control Flow

**How does it run?** Current systems fall into five structures. MOKA ([Liu et al., 2024](#ref-liu2024)), VoxPoser ([Huang et al., 2023](#ref-huang2023)), and ReKep run a fixed loop in which the VLM fills in values; HAMSTER and ENPIRE ([Xiao et al., 2026](#ref-xiao2026)) are two-level hierarchies; in Guava, CaP-X ([Fu et al., 2026](#ref-fu2026)), and Agent as Policy the model steps through calls; Code as Policies, ASPIRE, and GaP ([K. Chen et al., 2026](#ref-chen2026gap)) write a program and run it without the model; TypeGo is a concurrent, event-driven runtime.

<Figure wide caption="How control flow runs in surveyed systems.">
  <ControlFlowMap />
</Figure>

**Who decides, and what triggers the next step?** Decisions are written in a program or made by the model step by step; steps follow one another or are triggered by events. One system can use all four combinations:

|  | Programmatic decisions | Model-mediated decisions |
|---|---|---|
| **Sequential** | Skill composition; code as policy | ReAct; explicit VLM calls |
| **Event-driven** | Sensor-triggered rules and recovery | Event-triggered VLM replanning |

**What is the unit of execution?** A reach takes seconds, and the cup may move meanwhile, so the unit is a task: an action that keeps running after the call that started it returns, and can be updated or cancelled. (Code here uses the API of roborun, described in [a companion post](../roborun/).)

```python
g = start(grasp("cup"))     # returns at once; the grasp keeps running
g.update(target=new_pose)   # redirect it while it runs
await g.cancel_and_wait()   # returns when the arm is at rest
```

Cancelling must be distinct from having stopped, since control authority depends on it. A program changed mid-run should likewise let the step under way finish and continue from shared state, not from the old program's variables.

<Figure caption="A task's lifecycle. Requesting cancellation moves a task to cancelling, not cancelled: the arm is still moving. Click the transitions to step through it.">

### Managing Data

Should a tool be a **function call** or a **service**? A function call, like Guava's `get_position`, halts the caller and keeps nothing between calls, so a segmenter called per frame cannot tell whether this cup is the last one. A service keeps its state, answers while the program works, and says how fresh each answer is.

<Figure wide caption="The same segmentation model as a function call, which halts the program and keeps nothing, and as a service, which keeps its state and answers while the program works.">
  <DataPaths />
</Figure>

Shared state needs the same care: each value should say when it was observed and by whom, and a reader should be able to refuse one that is too old.

```python
cup = world.get("cup", max_age=0.3)   # StaleData if older
```

Messaging layers and frameworks such as ROS 2, Ray, and Temporal each cover part of this, but none says who may command the arm, when a command goes stale, or how conflicting behaviors are arbitrated.

## Future Work

Imagine every model call were instant. The arm would still take seconds to move, the cup could still be nudged meanwhile, a cancelled motion would still have to stop, and a bad command would still have to be caught. Stronger models make the software around them thinner; they do not remove the need for the system. Open questions remain: how to trace and undo a change to a running program, where the boundary between thin tools and rich skills should sit, and whether a safety layer independent of the model can still allow useful behavior. [roborun](../roborun/) is our first answer.

> A good system should not prescribe how intelligent a robot agent must be. It should provide the abstractions to express, coordinate, and evolve different forms of robotic intelligence, and keep the robot safe while it does.
